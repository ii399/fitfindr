# Acceptance criteria — FitFindr

Five criteria that say what "working" means for this agent, written in unit 3
**before** any results existed.

An acceptance criterion names a target: a number, a count, a rate, or something
a person could plainly observe. *"The agent handles errors"* is an opinion.
*"When search returns nothing, the agent stops before calling the second tool,
in 5 of 5 tries"* is a criterion.

Under each one, write a sentence or two on **why that target** and not a
stricter one. A reason that says something about your tools, your loop, or the
data earns credit; *"80% seemed reasonable"* does not.

> Missing your own targets next unit costs you nothing. Setting a target so
> easy you can't miss it does.

**Two are written for you. You write three.**

---

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three
tool calls and returns a fit card — in at least 4 of 5 tries.

**Why this target:**
My search tool uses keyword matching, so some user queries may not match the exact words in the clothing listings. A target of 4 out of 5 allows for occasional search mismatches while still requiring the agent to complete the three-tool workflow successfully most of the time.

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling
`suggest_outfit` and returns a message naming what to change — 5 of 5 tries.

**Why this target:**
A target of 5 out of 5 is reasonable because the agent can directly check whether the search returned any results. If no listings are found, it should always stop before calling suggest_outfit and tell the user what to change. This behavior can be controlled by a simple condition in the agent's workflow.

## 3. The selected item stays consistent between tools

<!-- YOU WRITE THIS ONE.

     How would you know that the item your search found is the same item the
     next tool received? Name something countable or observable.

     This is the criterion people find hardest, because state failure doesn't
     look like state failure — it looks like a tool problem. Something that
     compares session["selected_item"] against what actually reached
     suggest_outfit is the shape you're after. -->

For queries that return a matching listing, the item ID stored in session["selected_item"] must match the item ID passed to suggest_outfit in 5 out of 5 tests.

**Why this target:**

The agent stores the selected item in session state so the next tool can use it. Since the item is already saved, the agent should pass that exact item to suggest_outfit without changing it. A target of 5 out of 5 is reasonable because this is a direct comparison of item IDs, not a prediction made by the model.

## 4. The fit card includes the correct item price

<!-- YOU WRITE THIS ONE.

     The fit card calls a model, so the same input can produce different words
     each time. That's not a bug — it's the nature of the tool. So what would
     make it acceptable?

     Think about what you'd actually be unhappy to see. A caption that never
     mentions the price? Two different items producing the same opening
     sentence? A card longer than a caption anyone would post? Any of those can
     be turned into a number. -->

For queries that successfully generate a fit card, the card must display the selected item's correct price in at least 4 out of 5 tests. Equivalent currency formatting is acceptable, as long as the numerical price matches the selected listing. For example, $24, $24.00, and 24 dollars should all count as correct if the selected listing costs $24.

**Why this target:**

The fit card is generated by an AI model, so its wording may change between runs. However, the item price is important information that should come from the original listing. A target of 4 out of 5 allows for occasional formatting or generation mistakes while still requiring the card to provide accurate information most of the time.

## 5. Search results respect the user's budget

<!-- YOU WRITE THIS ONE TOO.

When a user specifies a maximum price, the agent returns only clothing items priced at or below that amount in 5 out of 5 tests. The test checks every listing returned by search_listings(), not just the final item selected by the agent. 


**Why this target:**

The search tool uses clothing listings that already contain prices, so the agent should be able to compare each item's price against the user's budget. A target of 5 out of 5 is reasonable because checking whether a price is within a specified limit is a straightforward comparison that does not depend on the AI model's wording.
